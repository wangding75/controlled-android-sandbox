## 3. 三条主调用链的实际差别

### 3.1 包导入到 Application 启动

**CAS：** PackageAuthority 的不可变修订与虚拟包快照 → Broker session/generation → GuestRuntimeEnvironment → 平台 defining ClassLoader → AppComponentFactory → GuestLoadedApkBridge → Application attach → Provider prepare → Application.onCreate → ActivityThread 桥与首帧。源码已明确避免第二次构造 Application，也保留普通与 isolated 两条 loader 路径。[C01](D:/github/controlled-android-sandbox/app/src/main/java/com/warden/controlledsandbox/ApkImportManager.java:39) [C02](D:/github/controlled-android-sandbox/app/src/main/java/com/warden/controlledsandbox/VirtualPackageStateBuilder.java:425) [C06](D:/github/controlled-android-sandbox/sandbox-runtime/src/main/java/com/warden/controlledsandbox/runtime/guest/GuestRuntimeEnvironment.java:603) [C07](D:/github/controlled-android-sandbox/sandbox-runtime/src/main/java/com/warden/controlledsandbox/runtime/guest/GuestLoadedApkBridge.java:50) [C08](D:/github/controlled-android-sandbox/sandbox-runtime/src/main/java/com/warden/controlledsandbox/runtime/guest/GuestClassLoader.java:31)

**NBB：** BPackageManager 返回包信息 → BActivityThread 创建 package Context、取 LoadedApk → runtime/native/IO 配置 → 替换 bind data → makeApplication（含 fallback）→ providers 与 onCreate。可借鉴它把包信息、LoadedApk 和 native 路径在启动前统一的顺序，但 fallback 吞异常不能被当作正确的 Application。[N01](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/java/top/niunaijun/blackbox/app/BActivityThread.java:358) [N08](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/java/top/niunaijun/blackbox/core/IOCore.java:107)

**VA2017：** VClientImpl 获取虚拟包信息 → IOUniformer/NativeEngine → Context 与 bound App → LoadedApk.makeApplication → mInitialApplication → providers → onCreate。它是初始化顺序的有效参照，但代码不知道后来出现的 AppComponentFactory/API36 行为。[V01](D:/github/t57-reference-sources/VirtualApp/VirtualApp/lib/src/main/java/com/lody/virtual/client/VClientImpl.java:316) [V07](D:/github/t57-reference-sources/VirtualApp/VirtualApp/lib/src/main/java/com/lody/virtual/client/NativeEngine.java:26)

**要补的是每个阶段所见信息一致及失败可定位。** 不是再造一套人工生命周期；新 Chrome NPE 的第一个任务是取得精确栈。

### 3.2 Service / Provider 的 owner 分类

**CAS 当前：** GuestContext → 虚拟 PMS；Service miss 时经原始宿主 PMS 尝试允许的 exported system Service；Provider 无虚拟 descriptor 时尝试允许的系统 Provider；符合条件走宿主真实 transport，虚拟目标走 Broker。剩余 Service miss 抛 `NO_GUEST_SERVICE_MATCH`，剩余 authority 抛 `CONTENT_PROVIDER_AUTHORITY_NOT_VIRTUALIZED`。[C10](D:/github/controlled-android-sandbox/sandbox-runtime/src/main/java/com/warden/controlledsandbox/runtime/guest/GuestIntentResolver.java:59) [C11](D:/github/controlled-android-sandbox/sandbox-runtime/src/main/java/com/warden/controlledsandbox/runtime/guest/HostPackageManagerBridge.java:93) [C12](D:/github/controlled-android-sandbox/sandbox-runtime/src/main/java/com/warden/controlledsandbox/runtime/guest/GuestContextComponentRouter.java:148) [C13](D:/github/controlled-android-sandbox/sandbox-runtime/src/main/java/com/warden/controlledsandbox/runtime/guest/GuestContentProviderFrameworkInterceptor.java:111)

**NBB/VA：** 两者均有虚拟组件与平台组件的分流。VA 的外部 provider 分支取得真实 holder 后包装 provider；无 holder 可以返回 null。NBB 的 provider 分流有显式 authority 集合，Service 有回原方法的分支，PMS resolveService 在虚拟 miss 后回真实 PMS。[N03](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/java/top/niunaijun/blackbox/fake/service/IActivityManagerProxy.java:132) [N04](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/java/top/niunaijun/blackbox/fake/service/IPackageManagerProxy.java:107) [V03](D:/github/t57-reference-sources/VirtualApp/VirtualApp/lib/src/main/java/com/lody/virtual/client/hook/proxies/am/MethodProxies.java:850) [V04](D:/github/t57-reference-sources/VirtualApp/VirtualApp/lib/src/main/java/com/lody/virtual/client/hook/proxies/pm/MethodProxies.java:439)

据此得到一个可执行的通用修复方向：把“正常没有可选服务/提供者”与“权限拒绝/隔离策略拒绝/适配器坏了”分开。平台 bindService 存在合法 false 返回，acquireContentProviderClient 在找不到 provider 时可以为 null；不能把所有 miss 都提升成杀死 SDK 线程的异常。这是对源码和平台合同的推断，需用原生直装与 CAS fixture 验证每个具体 API 的返回/异常差异。[Context 合同](https://developer.android.com/reference/android/content/Context.html)、[ContentResolver 合同](https://developer.android.com/reference/android/content/ContentResolver.html)。

这也不意味着允许所有宿主组件：导出、可见性、权限、物理 userId、同名虚拟包优先和回包身份都要保留。

### 3.3 Native 加载与边界

**CAS：** 对已加载 Guest ELF 的 PLT/GOT 进行重定位替换，late dlopen 后刷新；连 libc `syscall()` 入口也有有界代理。它明确区分普通 ABI 与翻译 ABI，拥有 FD/路径/网络/loader 模块；不能继续笼统写“没有 syscall 支持”。但 inline SVC/SYSCALL、自定义加载器等不能由同一 PLT 机制完全约束。[C20](D:/github/controlled-android-sandbox/sandbox-native/src/main/cpp/native_hook.cpp:319) [C21](D:/github/controlled-android-sandbox/sandbox-native/src/main/cpp/native_interceptors.cpp:1347) [C22](D:/github/controlled-android-sandbox/sandbox-native/src/main/cpp/native_loader.cpp:216)

**NBB：** Java IOCore 建重定向规则，UnixFileSystem JNI 方法执行路径变换；Runtime.nativeLoad hook 按 API 分签名，主要记录后调用原函数。其 FileSystemHook::init 只解析 open/open64 原函数并记录日志，没有把 new_open/new_open64 安装进目标，因此这个文件的存在不能计作成功的 libc hook。[N08](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/java/top/niunaijun/blackbox/core/IOCore.java:107) [N09](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/cpp/Hook/UnixFileSystemHook.cpp:71) [N19](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/cpp/Hook/FileSystemHook.cpp:66) [N20](D:/github/t57-reference-sources/NewBlackbox/Bcore/src/main/cpp/Hook/RuntimeHook.cpp:26)

**VA2017：** IOUniformer 对当时 libc 与内部 linker 符号做 Hook。**VA PRO 日志：** 后续增加 seccomp-BPF、32 位 seccomp、execve/openat2/faccessat2、重入处理等。这能证明商业版公开演进方向，不能推出当前 CAS 应如何实现 seccomp，也不能把 seccomp 拦截与强安全隔离画等号。[V08](D:/github/t57-reference-sources/VirtualApp/VirtualApp/lib/src/main/jni/Foundation/IOUniformer.cpp:639) [V12](D:/github/t57-reference-sources/VirtualApp/README.md:261)

当前目标为受信任商业 APK 的兼容执行。保留 CAS `EXPLICITLY_TRUSTED / BEST_EFFORT_COMPATIBILITY` 的已有边界；完整 hostile-native 隔离与商业 anti-detection 等价均不是首批 App 跑通的先决条件。

## 7. 两阶段切分与完成标准

**阶段一：** 已知的通用断点、可移植复现、签名与身份、组件生命周期、短 native/包/调度回归，全部在模拟器/AVD 优先处理。主基线 API35/36，旧 API 只补受影响入口；没有 x86_64 APK 时使用已验证的等价 fixture，并明确保留 ARM64 业务待验，不能用 MuMu 的翻译执行宣称真实 ARM64。

**阶段二：** 先在当前小米跑通 Chrome 与夸克的可操作业务 smoke，再用仓库已有钉钉、红果、番茄样本检查通用性；随后硬件、HyperOS 和短恢复，冻结拟交付版本。32位、GMS、ARM64 16KB、API37 根据实际目标触发，不让额外平台范围拖延本机首批闭环。

**最后才执行：** 大规模冷热启动/多用户/压力/完整历史回归（P2-90），最后是同一候选版本 8 小时净运行稳定性（P2-91）。本次把旧 KI-R03-032 的长稳债务放回最终尾部，没有把 8 小时设成每个修复任务的前置。

首帧可见、BASIC_SMOKE 可操作、登录业务成功、长稳通过、VA PRO 等价是不同结论，必须分开。默认先把 Chrome/Quark 作为首批必达；扩展 App 和需要账号的功能在 P1-01/P2-01 冻结范围，未提供账号或样本就保留明确未执行项。任何被选为本次必需功能的项目都不能在最终门禁以 NOT_TESTED 通过。

工期为开发估算，不是完成保证。任务详情中的循环次数、性能和资源阈值是本计划提出的验收门槛，不是从 VA PRO 日志推导的实现事实；执行前冻结，执行后不得为通过而改线。顺序、依赖与每个任务的操作/验收见 `02_两阶段执行任务书.md`。

## 8. 采用的公开平台核对

本次外部核对只使用官方资料；它们补充运行合同，不能替代对用户给定参考源码的研究。

- Trichrome 将共享 native 库放在第三个共享 APK，涉及 android_dlopen_ext、RELRO 与后续 JNI 加载，因此单独复制 Chrome base.apk 不能证明启动依赖齐全。[Chromium Android native libraries](https://chromium.googlesource.com/chromium/src/+/main/docs/android_native_libraries.md)。本页含历史变体描述，具体 Chrome148 的实际构建形态仍以冻结 APK 为准。
- bindService 的未找到返回与权限异常应按具体重载核对；Provider client 可以合法为空。[Context](https://developer.android.com/reference/android/content/Context.html)、[ContentResolver](https://developer.android.com/reference/android/content/ContentResolver.html)。
- API34+ 的目标应用动态代码加载有只读文件要求，是 split/插件复现的依据。[Android14 行为变更](https://developer.android.com/about/versions/14/behavior-changes-14)。
- 16KB 需要检查实际设备页大小、ELF/打包与动态执行，API 号本身不能替代测试。[Android 16KB 支持指南](https://developer.android.com/guide/practices/page-sizes)。

尝试获取 Android16 LoadedApk 在线分支时未成功读取，因此本报告没有把未读到的 Android16 AOSP 行号作为论据。进入涉及隐藏 API 的实现任务时，必须补齐与实际平台相符的 AOSP/系统签名及复现证据。
